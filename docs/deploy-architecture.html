AiNaiDee — server deployment architecture

Low-level view of what runs on the Ubuntu box. Procedure and open questions are in deploy.md.

1. Runtime topology

What exists on the server after docker compose up -d has completed.

Ingress flow
  • A visitor opens the browser and the client performs WebGL/WebGPU detection and grading.
  • DNS for ainaidee.com resolves to the Ubuntu host.
  • Caddy handles HTTPS termination and ACME certificate renewal.
Caddy container (caddy:2-alpine)
  • TLS termination and ACME renewal.
  • gzip and zstd compression.
  • Redirects /og/*.png to .jpg.
  • Marks /_astro/* assets immutable for cache control.
  • Applies security headers.
App container (ainaidee:latest)
  • Runs node dist/server/entry.mjs with @astrojs/node standalone.
  • Environment variables: HOST=0.0.0.0 PORT=4321.
  • Runs as the node user.
  • Serves static files from dist/client and server routes from dist/server.
  • The runtime app bundle includes only @libsql/client as a dependency.
Storage and environment
  • caddy_data stores certificates and access logs.
  • caddy_config stores Caddy configuration.
  • The host can provide TURSO_DATABASE_URL and TURSO_AUTH_TOKEN in /.env.
Networking note
  • Caddy and the app communicate over the Docker bridge network named web.
  • Caddy reverse proxies to http://app:4321.
  • The app also publishes 127.0.0.1:4321 so an existing host reverse proxy can reach it without exposing it publicly.
Telemetry
  • The app may send metrics to Turso via /api/runai/metrics.
  • Telemetry only works if TURSO_DATABASE_URL and TURSO_AUTH_TOKEN are set.
Why loopback publishing matters

Caddy reaches the app over the internal Docker network, so the app does not need a public port. Publishing it on 127.0.0.1 keeps it isolated and allows another reverse proxy to use the same app port if needed.

2. Image build pipeline

Two-stage build: the first stage compiles and produces the site, and the second stage ships only the runtime.

Stage 1 — builder
  • Base image: node:24-bookworm-slim.
  • Install pnpm@11.1.3.
  • Copy package manifests first so dependency installation works with --frozen-lockfile.
  • Install app dependencies for canirun-ai, excluding packages/runai.
  • Copy the repository and build with pnpm build.
  • Build renders 83 OG images using sharp and resvg and requires about 2 GB RAM.
Stage 2 — runtime
  • Base image: node:24-bookworm-slim.
  • Use docker/runtime-package.json as the runtime manifest.
  • Install production dependencies only: npm install --omit=dev.
  • Copy the built dist directory from the builder.
  • Run as user node, expose port 4321, and use a healthcheck against /api/models.
  • Startup command: node dist/server/entry.mjs.
Runtime dependency rule

The runtime image must include only packages actually imported by dist/server/entry.mjs. If you add a new server-side dependency, add it to docker/runtime-package.json too.

3. Request routing — what needs the server and what does not

Most pages are served statically from the prerendered client. Only a small set of routes run on the server.

Static pages
  • /, /design, /tier, /compare, /why, /docs
  • /model/:id, /device/:id, /license/:id
  • /og/*.jpg, /sitemap-index.xml, and /_astro/*
  • These are served from dist/client with no server-side execution.
Server routes
  • GET /api/models — returns the catalog.
  • GET /api/models/:id — returns model details.
  • POST /api/compatibility — runs compatibility logic.
  • POST /api/recommend — runs recommendations.
  • POST /api/runai/metrics — writes telemetry to Turso.
Core takeaway

Hardware detection and grading happen in the visitor’s browser. The server exists mainly for the JSON API routes. Remove those APIs and the site becomes a static site without Node runtime.

4. Deploy and update flow

First deploy
  1. Confirm the domain points to the server.
  2. Clone the repository.
  3. Optionally add .env for telemetry.
  4. Run docker compose up -d --build.
  5. The Docker build creates the app image and starts Caddy on ports 80 and 443.
  6. Caddy obtains ACME certificates and stores them in the caddy_data volume.
  7. The site goes live over HTTPS.
Updates
  1. Pull the latest code from Git.
  2. Run docker compose up -d --build again.
  3. The build reuses cached layers where possible.
  4. The app container is recreated; Caddy remains running and certificates survive.
  5. Optionally run docker image prune -f to remove old images.

Failure modes to check first

Symptom Almost certainly
Caddy exits immediately on start Another process already owns 80/443. Remove the Caddy service and use the existing reverse proxy.
Certificate never issued DNS is not propagated yet, or port 80 is blocked by a firewall.
Build killed partway through The build ran out of RAM during OG image generation. It needs about 2 GB.
Build fails on an Astro internal import The Astro adapter version is newer than 10.1.0.
Site up but a POST API 500s TURSO_* is unset, or a required server dependency is missing from docker/runtime-package.json.
Links and OG images point at the wrong domain SITE_URL is baked into the build. Rebuild to correct it.
